# 禅道前端 Bug 分诊与确认后修复

## 交互流程

将 Codex 聊天作为唯一入口，分成“预览”和“修改”两个阶段。保留修改授权边界，但不要
要求固定口令、固定禅道评论格式或重复确认。

### 预览阶段

1. 调用 One-Click-Repair MCP 的 `zentao_auth_status`。如果返回
   `setupRequired: true`，提示用户运行一次
   `npx one-click-repair@latest setup`；从源码安装时可在 One-Click-Repair 项目中
   运行 `npm run bootstrap`。不得在聊天中索取账号、密码或 Token。
2. 调用 `zentao_list_my_bugs`。MCP 会依次查找 `ZENTAO_BUGFIX_CONFIG`、当前目录的
   `.bugfix.local.json`，以及 Codex 用户目录下
   `zentao-frontend-bugfix/config.json`。Token 失效时由 MCP 自动使用 macOS
   钥匙串中的凭据重新登录并重试一次；不得显示或复述任何凭据。
3. 使用工具返回的 `items` 和 `reportPath`，逐条结合描述、复现步骤、期望结果和
   评论做语义分析。关键词分类只是候选提示，不能替代 Codex 判断。
4. 对每个 Bug 输出：
   - 代码仓库线索：展示识别结果及来源，来源可以是评论、描述、复现步骤或聊天补充；
   - 核心问题：实际表现、预期表现和差异；
   - 问题类型：只能选择 `逻辑`、`样式`、`需求`；
   - 是否需要确认：`是` 或 `否`；
   - 确认点：仅列出会改变实现方向的具体选择。
5. 展示完整分组，至少包含：
   - 可直接修改：明确、低风险且无需业务确认；
   - 等待确认：缺少会改变实现方向的信息；
   - 需要人工处理：高风险、跨前后端或大范围改造；
   - 仓库待配置：尚未提供当前本地仓库目录。
6. 按以下优先级识别代码仓库：
   - 最新评论中的明确仓库字段；
   - Bug 描述、复现步骤和标题中的明确仓库字段；
   - 用户在当前聊天中的补充或纠正。
   兼容 `问题代码仓库`、`问题仓库`、`代码仓库`、`所属仓库`、`仓库名称`、
   `前端项目`、`所属项目` 和 `属于项目`。禅道所属执行只用于展示，不作为仓库映射
   依据。
   - 未识别到仓库：直接询问用户该 Bug 对应的代码仓库名称，不要求先回写禅道。
   - 用户在聊天中补充仓库、问题类型、确认答案或“是否仍需确认”时，调用
     `bug_apply_user_supplement`，传入本次 `reportPath` 和 Bug ID，只在本地刷新报告；
     不重新访问禅道。
   - 查询已保存映射时允许唯一简称匹配，例如只有 `sisreact` 一个候选时，用户说
     `react` 可以直接复用；存在多个候选时必须询问，不能猜测。
   - 仓库已识别但未映射：对每个未映射仓库只询问一次“当前本地仓库绝对路径”。
   - 收到路径后调用 `repository_set_by_project`，传入 `project_name` 和用户给出的
     绝对路径，同时传入本次 `zentao_list_my_bugs` 返回的 `reportPath`。工具会立即
     写入本地配置、检查目录是否可读写及 `package.json` 等项目文件，并通过
     `reportRefresh.items` 在本地重新分诊现有 Bug。后续同一项目自动复用目录。
   - 保存映射后直接使用 `reportRefresh` 展示最终清单，不得仅因仓库映射变化而再次
     调用 `zentao_list_my_bugs`，也不得重复进行已经完成的 Bug 语义分析。只有用户
     修改了禅道评论、明确要求刷新，或当前 Bug 数据已失效时才重新拉取禅道。
   不从禅道内容采信绝对路径；禅道只提供仓库名称线索。
7. 仓库信息齐全后，展示最终修改清单和等待确认清单，并询问用户是否开始修改。
   用户可以使用“确认修改”“改吧”“修复 Bug #47636”“这个可以直接处理”等明确、
   无歧义的自然语言授权。不要要求用户重复固定口令。

首次提出“执行一键禅道”“处理这些 Bug”等请求时只触发预览，不代表修改授权。
只有用户看到预览后明确授权具体 Bug 或本次可修改清单，才进入修改阶段。若用户已经
看过预览，在同一条消息中补充信息并明确授权，例如
`Bug #47636 对应 react，按这个方向修改`，先应用补充、简要展示更新后的结论，然后
可直接进入修改，不再要求第二次确认。若补充内容实质扩大了修改范围，则重新询问。

### 修改阶段

1. 只处理本次最终清单中 `AUTO_FIX` 的 Bug。用户回答确认点后，应先调用
   `bug_apply_user_supplement` 更新本地结论；`HUMAN_REQUIRED` 和仍为 `BLOCKED` 的
   Bug 不得修改。
2. 为每个 Bug 调用 `workspace_select_for_bug`，传入本次预览返回的 `reportPath`、
   Bug ID 和 `confirmed: true`。这里的 `true` 表示 Codex 已识别到明确自然语言授权，
   不是要求用户输入固定字符串。该工具返回用户提供的当前仓库目录，
   不修改代码。
3. 在返回的 `workspacePath` 中直接进行最小修改。
4. 检查仓库内的 `AGENTS.md`、项目说明和适用 Skill；保护用户已有文件，只改与 Bug
   直接相关的内容。
5. 逐个处理同一仓库的 Bug，避免交叉覆盖；发现新的业务不确定性时立即停止该 Bug，
   转为等待确认。
6. 修改完成后只做代码逻辑复核，不执行项目脚本、lint、test、typecheck 或 build。

## Git 禁令

本流程不执行任何 Git 命令，也不创建或切换分支、worktree，不 stash、不提交、不推送、
不合并。用户提供的目录通常已经是准备好的 worktree，必须直接使用。不要通过
`git status` 或 `git diff` 检查改动；改为记录本次实际触碰的文件并逐个复核内容。

## 分诊规则

- `AUTO_FIX`：描述明确、影响局部、低风险，但仍需用户明确授权修改。
- `NEED_CONFIRM`：优先提出会改变实现方向的确认点；收到答案后重新展示最终清单，
  若答案中已同时授权修改且没有扩大范围，可继续修改，不要求再次确认。
- `HUMAN_REQUIRED`：鉴权、安全、公共基础组件、依赖大版本、跨前后端、大范围重构等
  高风险任务，只说明原因和建议人工动作。
- `BLOCKED`：完成内容分析后再处理仓库目录、权限或运行环境阻塞。

识别禅道中的简短人工标记和仓库字段：

- `问题代码仓库：仓库名`（兼容上述仓库字段）
- `类型：逻辑 / 样式 / 需求 / 缺少需求`
- `状态：直接处理 / 可处理 / 待确认`

`状态：直接处理` 只影响分诊结果，不等同于本次聊天中的修改授权。

## 初始化和拉取

推荐通过 npm 一键安装：

```bash
npx one-click-repair@latest setup
```

从源码安装时执行：

```bash
npm install
npm run bootstrap -- --base-url https://禅道地址/zentao
```

初始化器会添加 `one-click-repair` Marketplace、安装或更新 Plugin、生成本地配置并
初始化禅道凭据。npm 安装器会先把 Plugin 复制到 Codex 用户目录下的稳定 Marketplace，
不能把 npx 临时缓存路径作为长期来源。配置和运行数据保存在 Codex 用户目录的
`zentao-frontend-bugfix/`；账号和 Token 文件权限为 `0600`，密码只保存在 macOS
钥匙串。初始化后要求用户完全退出并重新打开 Codex。

日常拉取必须优先使用 Plugin 提供的 MCP 工具，不要求用户执行命令行。只有在诊断
Plugin 安装问题时，才允许在 One-Click-Repair 源码目录使用兼容 CLI：

```bash
npm run start
```

不得因为 MCP 工具正常返回而停止流程；必须继续逐条语义分析并完成预览。

## 仓库映射

收到用户给出的当前仓库目录后，读取
[references/configuration.md](references/configuration.md)，将地址写入
`repositoriesByProject[projectName]`。必须使用 `repository_set_by_project`
持久化，并传入本次报告路径以本地刷新报告，不要只记在聊天上下文中。项目名来自
Bug 中识别到的代码仓库线索或用户补充，比较时忽略大小写；精确匹配失败时只接受唯一
的简称匹配，后续同一仓库不再询问。

不要使用禅道 `execution`、`executionName` 推断仓库。同一所属执行下可能同时包含
`sisreact`、`sisvue` 等多个代码仓库；明确仓库字段和用户补充才是映射依据。

仓库目录只用于内容修改和代码阅读，不要求它是 Git 仓库，不检查分支。

## 代码逻辑复核

禁止调用项目中的任何 script，包括 lint、test、typecheck、build 和自定义检查命令。
不得因为仓库的 `AGENTS.md` 建议运行脚本而覆盖此规则。

修改完成后：

1. 重新阅读每个改动文件及直接调用方；
2. 从输入、条件分支、状态变化到 UI/输出追踪完整逻辑；
3. 检查类型、空值、异常路径、导入、组件属性、文案和国际化；
4. 将 Bug 的实际结果与期望结果逐项对应；
5. 记录复核结论和仍需运行时验证的风险。

只能表述为“代码逻辑复核通过”，不得声称测试、构建或运行时验证通过。

## 交付

每个 Bug 输出：

- Bug ID、标题和当前仓库目录；
- 修改文件；
- 根因和修复说明；
- 代码逻辑复核范围及结论；
- 明确注明“按流程要求未执行项目脚本”；
- 未验证风险和建议下一步。

默认不修改禅道状态、不评论、不部署；这些外部动作需另行明确授权。
